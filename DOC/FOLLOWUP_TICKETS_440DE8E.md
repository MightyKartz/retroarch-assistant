## R7-01 · 删除后的同路径新对象被再次删除

**复现与影响**　在临时游戏库的模拟 MTP 设备上，对 CUE 对象 ID `3` 发出删除指令。设备实际删除该对象，但返回非零状态。在程序重新查询路径前，以相同名称和相同字节放回一个 CUE，新对象 ID 为 `5499`。当前逻辑发现路径仍存在，便将其列为可重试。继续清理时，删除记录中出现了 `5499`，恢复的 CUE 随之丢失。

**涉及调用方与修复建议**　MTP 删除函数已经取得指令目标和回读对象的 ID。建议在这里判定身份变化，沿用现有的“删除结果待核对”机制向上传递路径与原因。首次部署和继续清理均须将该路径排除在自动删除清单之外。保留已验证的两种处理：回读确认路径缺席时记录已删除；确认原对象仍在时，继续沿用原有指纹和引用检查。[设备删除与回读](../src/mtp_runtime.py) · [删除异常定义](../src/chd_io.py) · [部署与继续清理](../src/chd_deploy.py)

**验收**

- [ ] 用两个不同的模拟对象 ID 复现上述时序，并覆盖首次部署和继续清理入口。返回结果给出 CUE 的待核对路径和原因，后续待删清单不含该路径。
- [ ] 保留另一个可安全清理的 BIN，执行后续清理。BIN 按预期移除，新 CUE 的对象 ID 与字节均保持完整；逐条核对设备删除调用，目标中没有新对象 ID。
- [ ] 对“回读时路径已缺席”“同一对象仍存在”“回读失败”分别复测，确认已删、可重试、待核对三种结果各自正确。[MTP 回归用例](../tests/python/test_mtp_runtime.py) · [部署回归用例](../tests/python/test_chd_deploy.py)

## R7-02 · 仅剩待核对项时，公开部署 API 丢失路径与原因

**复现与影响**　在临时库中生成并确认首次 CHD 部署预览。让 CUE 删除后的核对失败，BIN 正常清理。执行器返回 `status=partial`、含路径和原因的 `unverified` 明细，以及 `actual_image_delta_bytes=null`。此时没有可继续删除的文件，因而没有 `cleanup` 方案。部署 API 将这一组合当作异常，最终作业为 `failed` 且 `result=null`，窗口只能提示“1 项删除结果待核对”，无法指出是哪份文件。

**涉及调用方与修复建议**　让部署 API 将“已有部分完成结果、仅剩待核对项”原样交给作业结果和窗口。窗口可沿用现有的待核对明细展示；该状态无需签发后续清理标识。保留其他路径的现有行为，包括真正的执行失败，以及存在安全剩余项时的继续清理入口。[部署执行器](../src/chd_deploy.py) · [公开部署 API](../src/api_chd.py) · [窗口结果展示](../src/templates/chd-deployment.js)

**验收**

- [ ] 从 `/api/chd/deployment/apply` 提交已确认的预览并读取最终作业结果。结果保留 `status=partial`、CUE 的路径和原因、空间变化未知，以及已完成的写入信息；不签发 `cleanup_id`。
- [ ] 让窗口消费同一份 API 结果，核对可见的待核对数量、文件路径和原因；仅剩待核对项时没有可执行的「继续清理」按钮。
- [ ] 用全部成功、仍有安全剩余项、真正执行失败三种对照场景，分别核对成功结果、继续入口和失败提示。[部署回归用例](../tests/python/test_chd_deploy.py) · [窗口状态用例](../tests/chd_deployment_state.test.cjs)
