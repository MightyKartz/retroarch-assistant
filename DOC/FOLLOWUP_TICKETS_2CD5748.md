## REV-01 · 切换 CHD 记录后仍可触发上一份记录的清理

**复现与影响。** 在临时库中让 A 完成引用切换并中断源镜像清理，出现「继续清理」。打开转换记录 B，按钮仍可见，携带的仍是 A 的方案。用户可能在查看 B 时删除 A 的原镜像。另一个复现场景是第一份源文件已删、第二份删除失败，待清理列表仍包含第一份。

**涉及与改法。** 在服务端任务上下文保存已经核验的剩余方案，继续请求只引用对应任务标识。桌面端在关闭、切换记录或重新预览时统一撤下按钮并清空旧标识；只接收属于当前记录的结果。根据已确认的删除结果生成待清理明细。沿用现有源指纹、引用和目标文件校验。[部署界面](../src/templates/chd-deployment.js) · [公开 API](../src/api_chd.py) · [清理执行](../src/chd_deploy.py)

**验收**

- [ ] A 清理中断后切换到 B，B 页面没有 A 的入口；延迟到达的 A 结果也不会把入口带回 B。
- [ ] 使用公开 API 从 A 的部分完成结果继续，只清理该任务仍待处理的文件；旧计划不因重新提交而重复执行。
- [ ] 模拟第一份删除成功、第二份失败，明细与磁盘一致；重新引用或内容变化的源文件得到保留和说明。

## REV-02 · 目录删除中途取消后，已删除文件没有进入同步记录

**复现与影响。** 在临时目录放入 3 个文件，删除第一个后取消。磁盘只剩 2 个，任务返回 `cancelled` 且结果为空。前端只在全部删除成功时登记变动，于是已经删除的游戏仍可能出现在列表中。

**涉及与改法。** 后端保留已经确认删除的路径；调用方处理部分结果时刷新目录、显示完成情况，并仅为已删除项登记同步。目录尚存在时，整目录删除规则会误伤剩余条目，应只提交实际删除的范围。[文件操作](../src/game_file_actions.py) · [作业状态](../src/job_manager.py) · [文件页与同步登记](../src/templates/game-files.js)

**验收**

- [ ] 开始前取消时三个文件均在；中途取消时界面明确报告部分删除，已删明细与磁盘逐项一致。
- [ ] 更新列表后只移除已删除文件的条目，剩余文件仍可启动；完整删除后仍能按原流程同步整个目录。

## REV-03 · 全库补全取消后显示完成

**复现与影响。** 取消一个尚未处理首个列表的全库补全任务，`apply_review` 跳出循环并正常返回，作业管理器将任务标为 `completed`。用户无法区分完整运行和提前停止。

**涉及与改法。** 让全库执行方传递实际停止原因及已处理范围，再由任务层和完成提示消费。修改共享任务状态前，同时核对 REV-02 与“操作已完成才收到取消请求”的调用路径。[批量执行](../src/batch_review.py) · [任务 API](../src/api_playlists.py) · [状态管理](../src/job_manager.py) · [完成提示](../src/templates/tasks.js)

**验收**

- [ ] 分别在首个列表前和完成一个列表后取消，通过任务 API 与桌面提示核对取消状态、已处理数量和实际写入。
- [ ] 全部写入已完成才收到取消请求时，保留成功结果；普通完整运行仍显示完成。

## REV-04 · 同名替换双重失败时，恢复提示与实际文件不符

**复现与影响。** 对临时同名目录依次注入发布失败和回退失败。旧件保留在移开的路径，错误文案同时给出新版暂存路径，但外层清理已删除暂存件。桌面摘要只显示失败文件名，旧件的真实位置也不可见。

**涉及与改法。** 明确双重失败后的实际保留策略，返回可找回对象的真实路径和失败步骤，在桌面结果中显示。现有测试仅检查错误字符串里有路径前缀，需改为同时核对目录和文件内容。[替换与异常清理](../src/game_file_actions.py) · [桌面摘要](../src/templates/game-files.js) · [故障注入测试](../tests/python/test_game_file_ops.py)

**验收**

- [ ] 双重失败后，从界面给出的路径可读取并校验旧件；每个声称保留的对象均实际存在。
- [ ] 仅发布失败且回退成功时，原路径内容完整；正常替换与发布前取消仍通过。

## REV-05 · 合法 JSON 中的损坏条目仍可阻断整库同步

**复现与影响。** 将有效列表与 `{"items":null}` 或 `{"items":[null]}` 放入同一库，更新正常游戏的路径。预览分别抛出类型或属性异常。另一种情况是好列表可读但没有匹配项、坏列表读取失败，界面会误称「所有列表都无法读取」。

**涉及与改法。** 在每份列表的读取边界一次校验对象、条目数组及参与路径匹配的字段，把失败归到对应列表；校验完成后再累计该列表的匹配和变更。预览向界面提供足以判断成功读取与读取失败数量的信息。[同步预览与应用](../src/game_file_sync.py) · [结果展示](../src/templates/game-files.js)

**验收**

- [ ] 两种损坏样例分别与有匹配项的健康列表混用，健康列表可以预览并写回，坏列表字节不变。
- [ ] 混合库零匹配时明确报告健康列表无匹配和部分读取失败；仅在确实全部读取失败时显示全失败。

## REV-06 · 批量图片写入丢失 MTP 旧对象清理告警

**复现与影响。** 让模拟设备成功发布新图片，但删除旧对象失败。单文件 `write` 返回残留路径，`push_directory` 忽略返回值，因此批量任务无法显示设备上的旧对象。

**涉及与改法。** 目录上传汇总各图片的残留路径；播放列表传输合并列表与图片告警；单列表和全库补全结果均需传达“写入已成功”和具体残留位置。[目录上传](../src/mtp_runtime.py) · [列表传输](../src/playlist_transport.py) · [批量汇总](../src/batch_review.py) · [任务提示](../src/templates/tasks.js)

**验收**

- [ ] 模拟多张图片中一张旧对象清理失败，最终任务能定位该旧对象，新图回读正确，未再次发布。
- [ ] 同时出现列表和图片残留时两类告警均可见；无残留时正常完成。

## REV-07 · 粘贴成功后未定位副本；补齐两端平台证据

**复现与影响。** 后端目标名已修正。前端仍用 `result.path.split('/').pop()` 与目录项显示名称匹配。Windows 反斜杠路径和含百分号编码的 MTP URI 均可能导致复制成功却没有高亮副本。

**涉及与改法。** 让界面使用实际目标身份，例如用返回的目标路径与重读目录项的路径直接匹配，或由服务端返回最终显示名。重名产生的「副本」名称以实际结果为准。[复制实现](../src/game_file_actions.py) · [文件操作 API](../src/api_library.py) · [粘贴后定位](../src/templates/game-files.js)

**分别验收，不互相等待**

- [ ] **BUG-04 · Windows：** 在原生 Windows 上跨目录、跨盘粘贴，并覆盖目标同名；源目录没有意外副本，目标内容正确，实际新项目高亮。
- [ ] **BUG-05 · MTP：** 在掌机测试目录中粘贴含中文、空格和字面百分号的样例；重新列目录并读回核对名称和内容，确认普通名与同名副本都能定位。

## REV-08 · 校正剩余的恢复与继续清理说明

**问题与影响。** 中文 README 仍列出「操作恢复」与「恢复记录」。ROM 整理说明写有“同一预览下重试”或“继续清理”，实际应用入口会消费预览；当前继续清理 API 属于 CHD 部署。用户可能误判写入后的可逆性。

**涉及与改法。** 按现有用户入口逐项区分重新预览、任务重试、CHD 剩余清理和恢复旧内容。核对中英文入口及历史文档顶部的当前版本说明；历史流程明确标注其适用版本。[中文 README](../README.md) · [英文 README](../README_EN.md) · [ROM 整理说明](ROM_RELOCATION_AND_RECOVERY.md) · [CHD 说明](CHD_DEPLOYMENT_AND_RECOVERY.md) · [ROM 整理 API](../src/api_rom_storage.py)

**验收**

- [ ] 依次从当前指南查找 ROM 整理与 CHD 中断后的操作，每条说明均对应可用入口，能判断是否需要重新预览。
- [ ] 发布文案和两种语言的指南对永久写入、可重试步骤及可恢复内容表述一致。CHD 部分按 REV-01 最终行为核对。
