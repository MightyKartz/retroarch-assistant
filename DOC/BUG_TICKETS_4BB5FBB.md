# 文件写入与播放列表同步修复工单

审查基线为 `codex/confirm-buttons` 分支的 `4bb5fbb`。以下 9 张均待认领，编号为仓库内跟踪编号。复制路径问题拆为 Windows 和 MTP 两张，便于分别安排平台验证。审查基线的 620 项 Python 测试和 159 项 Node 测试均已通过，下列复现覆盖了既有测试遗漏的情形。

| 编号 | 优先级 | 工单 | 证据 |
| --- | --- | --- | --- |
| BUG-01 | P1 | 同名替换发布失败后，目标原件丢失 | 临时目录，注入重命名失败 |
| BUG-02 | P1 | 本地删除、复制未响应取消，任务却标为已取消 | 临时目录，实际执行取消与文件操作 |
| BUG-03 | P1 | 连续改名后，播放列表指向中间路径 | 临时 ROM 和 LPL，实际写回 |
| DOC-01 | P1 | 用户指南承诺已移除的自动备份与恢复 | 对照当前文档、实现和路由 |
| BUG-04 | P2 | Windows 粘贴将副本写回源目录 | Windows 路径语义模拟 |
| BUG-05 | P2 | MTP 粘贴将中文和空格写成百分号编码 | MTP URI 模拟 |
| BUG-06 | P2 | CHD 引用已切换，清理中断后无法从正常入口继续 | 临时库，真实 CHD 转换，注入清理失败 |
| BUG-07 | P2 | 一个损坏列表阻断整库文件同步预览 | 有效与损坏 LPL 混合复现 |
| BUG-08 | P2 | MTP 旧对象清理失败，写入仍报告成功 | 模拟设备返回删除失败 |

建议先处理前四张。BUG-01 与 BUG-02 共用文件操作模块，需联合验证「写入过程中取消」。BUG-03 与 BUG-07 共用同步预览入口，可共用测试库。涉及永久删除的验收均使用可丢弃的本地目录或设备测试目录。

## BUG-01 · 同名替换发布失败后，目标原件丢失

**复现与影响。** 在来源和目标目录分别建立同名 ROM，写入不同内容。确认替换，让暂存成功后的最后一次重命名失败。任务报告失败，目标原件和已复制的暂存件均消失，原列表的启动路径随即失效。

**调用方与修复建议。** 游戏文件页的添加／替换操作经 `/api/game-files/file-ops` 进入 `apply_add`。当前顺序为删除目标、发布暂存、异常时清理暂存。普通本地文件可利用同卷原子替换；本地目录和 MTP 可在本次操作内暂时移开旧对象，确认新对象就位后清理。回退也失败时，应报告可找回的对象位置。[文件写入](../src/game_file_actions.py) · [API](../src/api_library.py)

**验收**

- [ ] 分别注入复制失败和最终发布失败；目标原件内容可校验，任务结果说明故障发生在哪一步。
- [ ] 在本地文件、本地目录和模拟 MTP 上验证成功替换、跳过同名及发布前取消；成功时只留下预期目标。

## BUG-02 · 本地删除、复制未响应取消，任务却标为已取消

**复现与影响。** 创建含文件的临时目录，提交本地删除任务，先置取消标记，再执行删除。任务状态为 `cancelled`，目录实际已被删除。以同样方式运行本地复制，目标副本仍会生成。

**调用方与修复建议。** 文件进度框发出取消请求，API 已传入取消检查，但本地分支直接进入 `rmtree`、`copytree` 或 `copy2`。作业管理器又仅凭取消标记决定完成态。建议在开始写入前及支持中断的文件边界检查取消；进入不可中断阶段时，使界面、服务端结果和磁盘状态一致。修改共享任务状态前核对其他调用方。[文件操作](../src/game_file_actions.py) · [任务状态](../src/job_manager.py) · [进度框](../src/templates/game-files.js)

**验收**

- [ ] 开始前已取消，原目录完整，复制目标未创建。
- [ ] 进行中取消能区分已完成、部分完成与尚未执行；删除已实际完成时，界面不得显示为已取消。完成的改动仍能进入列表同步。

## BUG-03 · 连续改名后，播放列表指向中间路径

**复现与影响。** 创建指向 `A.nes` 的列表，在文件管理器依次改名为 `B.nes`、`C.nes`，最后更新列表。磁盘只存在 `C.nes`，预览和写回停在 `B.nes`，游戏无法从该条目启动。

**调用方与修复建议。** 文件页按顺序记录变动，`game_file_sync.preview` 对原路径只取第一条匹配规则。应按记录顺序推演每个条目的最终物理路径和删除状态，保留压缩包成员后缀。应用时仍要核对预览签名。[变动记录](../src/templates/game-files.js) · [预览与应用](../src/game_file_sync.py)

**验收**

- [ ] 连续改名只产生一次最终路径更新；先改目录再改其中的文件也能写到最终位置。
- [ ] 改名后删除得到移除条目；`pack.zip#inner.nes` 的成员名保持正确；未涉及的条目保持原值。

## DOC-01 · 更正用户对自动备份与恢复的预期

**复现与影响。** 桌面指南仍说明补全前自动备份、ROM 更新后可恢复旧版；英文 README 仍引导用户从设置恢复列表。当前版本已移除相关持久备份及恢复入口。用户可能在预期可撤销的情况下确认永久写入。

**修复建议。** 以现有写入流程和路由为准，核对中英文 README、桌面指南及当前使用的操作说明，分别写清补全、ROM 替换和永久删除的效果。历史版本说明可标明适用版本，仍然有效的数据包回滚等功能保留其原有说明。[中文 README](../README.md) · [英文 README](../README_EN.md) · [桌面指南](DESKTOP_GUIDE.md) · [实际路由](../src/api_routes.py)

**验收**

- [ ] 从当前指南按步骤操作，每个声称可用的撤销或恢复入口都能在对应功能中找到。
- [ ] 新用户在确认写入前可以判断原文件能否找回；中英文口径一致。

## BUG-04 · Windows 粘贴将副本写回源目录

**复现与影响。** 按 Windows 路径语义模拟，从 `C:\src\game.nes` 复制到 `D:\roms`，传给复制函数的目标是 `C:\src\game 副本.nes`。源路径被当作文件名拼接，覆盖了用户选择的目标目录。

**调用方与修复建议。** 文件页粘贴进入 `apply_copy`，现有实现用 `PurePosixPath(path).name` 读取本地文件名。本地分支使用宿主平台的 `Path(path).name`，同名副本继续在所选目标目录内命名。[复制实现](../src/game_file_actions.py)

**验收**

- [ ] Windows 上分别验证跨目录、跨盘符复制和目标同名；源目录没有意外副本。
- [ ] 文件和目录都能复制；返回路径、实际落盘位置和界面定位一致。

## BUG-05 · MTP 粘贴将中文和空格写成百分号编码

**复现与影响。** 模拟设备内粘贴 `仙剑 1.cue`，对生成的目标 URI 按设备规则解码一次，文件名仍为 `%E4%BB%99%E5%89%91%201.cue`。用户在设备上看到乱码形式的文件名。

**调用方与修复建议。** `apply_copy` 从已编码的 URI 直接截取文件名，随后 `mtp.join` 再编码一次。应从 `mtp.parse` 返回的设备路径段取得名称，由 URI 构造函数负责编码。[复制实现](../src/game_file_actions.py) · [MTP 路径处理](../src/mtp_runtime.py)

**验收**

- [ ] 对含中文、空格和字面百分号的文件／目录验证粘贴与同名副本，设备端对象名等于预期原文。
- [ ] 模拟设备用例通过后，在测试掌机上粘贴一份中文样例，并从目标目录重新读取核对。

## BUG-06 · CHD 引用已切换，清理中断后无法从正常入口继续

**复现与影响。** 用临时 CUE/BIN 转换得到 CHD，选择切换引用并清理原镜像，在首次清理时注入失败。列表已指向 CHD，旧文件仍占空间。再次预览提示原 CUE 或其引用已变化。直接把同一个内存计划交给执行函数可以重试，但 API 已消费该计划。

**调用方与修复建议。** 回传应用经 `api_chd` 消费预览，再由 `chd_deploy.start` 切换引用和清理。建议将部分完成结果返回给任务页，列明已切换的引用和待清理文件。提供仅针对剩余文件的继续入口，重新计算引用并核验文件指纹，保留原预览单次消费语义。[回传 API](../src/api_chd.py) · [回传执行](../src/chd_deploy.py) · [桌面入口](../src/templates/chd-deployment.js)

**验收**

- [ ] 从公开 API 或桌面入口完成「清理失败 → 查看结果 → 继续清理」，无需持有原 Python 计划对象。
- [ ] 已验证的 CHD 和已切换的引用不重复写入；旧文件发生变化或重新被其他列表引用时保留并说明原因。

## BUG-07 · 损坏列表阻断其他列表的文件同步

**复现与影响。** 同一库中放入有效的 `NES.lpl` 和 JSON 损坏的 `Broken.lpl`，仅修改 NES 游戏的文件名。全库同步预览直接抛出 `JSONDecodeError`，有效列表也无法取得更新方案。

**调用方与修复建议。** 文件同步预览逐个读取并解析列表。建议在单个列表的读取／解析边界记录失败，向界面返回文件名、原因及其余可处理项。用户确认后只写入成功核对的列表，并继续对预览范围做签名校验。[同步预览](../src/game_file_sync.py) · [预览结果界面](../src/templates/game-files.js)

**验收**

- [ ] 混合库显示坏列表和好列表各自的结果；确认后好列表路径正确，坏列表字节保持原样。
- [ ] 全部读取失败时明确显示失败并禁用应用；单个失败不得显示为“没有需要更新的条目”。

## BUG-08 · MTP 清理旧对象失败后仍报告成功

**复现与影响。** 在模拟设备中替换已有列表，让最后一次 `LIBMTP_Delete_Object` 返回失败。调用正常返回，目标列表已更新，但设备仍留有 `.plcn-*.old` 对象。重复操作可能持续占用空间。

**调用方与修复建议。** `mtp_runtime.write` 被播放列表、图片和 ROM 写回等路径复用。检查清理结果，区分「新内容已验证」与「旧对象清理失败」，并把残留位置传给相应任务。避免把清理失败展示为需要重新写入整份新文件。[MTP 替换](../src/mtp_runtime.py) · [播放列表写回](../src/playlist_transport.py) · [已有设备模拟测试](../tests/python/test_mtp_runtime.py)

**验收**

- [ ] 注入删除失败，目标新内容仍通过校验，任务能指出旧对象残留及其位置。
- [ ] 正常替换后目录中无临时对象；清理失败后的处理不会重复发布已写好的目标。
