## GF-04-R1 · 无冲突导入会覆盖执行中出现的目标

**复现与影响**　预览将本地 `free.sfc` 导入空目录。在执行已检查目标不存在之后、真正调用复制之前，于目标目录创建同名文件，写入不同内容。当前实现直接写入最终路径，覆盖刚出现的文件，并把该项报告为复制成功。已用临时本地目录复现。

**修复建议**　复用独立暂存路径，发布无覆盖授权的内容时使用具备拒绝已有目标语义的操作。出现同名时保留该对象，只清理本任务创建的暂存内容，并按已保留报告。核对文件选择器和 Finder 共用的导入入口，以及本地文件、目录和 MTP 各自的发布边界。[导入执行与发布](../src/game_file_actions.py) · [导入提交与结果展示](../src/templates/game-files.js)

- [ ] 用可控制的测试钩子在目标存在性检查后创建同名文件。执行结束后，外部文件字节保持原样，结果为「已保留」，没有计入成功复制或替换。
- [ ] 用同样方式覆盖本地目录目标。已有目录及其内容均保留，结果能定位该项。普通无冲突复制和已授权替换继续通过。

## GF-04-R2 · 整目录替换漏检已有文件内容的更新

**复现与影响**　预览替换整个 `Game/`，目标目录内已有 `keep.bin`。预览之后原地更新该文件内容。目标目录的修改时间和直属条目数保持一致，当前校验值也相同。执行后任务报告替换成功，更新过的 `keep.bin` 消失。已用临时本地目录复现。

**修复建议**　对明确批准替换的目录，保存并复核足以识别其成员和内容变更的依据。目录的时间和直属条目数不足以授权删除整棵目录。冲突对比仍可省略目录总大小。MTP 无法可靠核对时保留目标，并返回可供用户处理的原因。[目标校验与替换发布](../src/game_file_actions.py)

- [ ] 预览后修改现有文件内容，分别覆盖直属和嵌套文件。执行报告「目标已变化，已保留」，保留目录及更新后的内容，清理本任务暂存。
- [ ] 在暂存期间修改目录成员，发布前同样拦截。目标可完整核对且未变化时，仍能按原授权完成整目录替换。

## GF-03-R1 · MTP 断连丢失前面已确认的删除结果

**复现与影响**　批量删除至少两项。第一项成功删除，查询第二项类型时模拟 USB 断开。批任务抛出异常，第一项已确认删除的路径没有返回给播放列表同步。生成「未执行」条目时的设备查询也可触发同类丢失。已用模拟 MTP 复现。

**修复建议**　把当前项的设备查询和删除都纳入结果处理。停止后用已知的选择信息生成未执行条目，避免再次依赖已断开的设备。向前端返回已确认删除的结果，沿用现有规则登记同步。原有单项操作仍可调用。[批量删除](../src/game_file_actions.py) · [任务 API](../src/api_library.py) · [同步预览](../src/game_file_sync.py)

- [ ] 模拟第一项成功、第二项查询断连、第三项未执行。任务仍返回第一项已删、第二项失败及原因、第三项未执行，并且没有查询第三项设备状态。
- [ ] 在游戏文件页使用该任务结果打开同步预览，只移除确认已删的文件对应条目。部分删除的目录仍只同步其中实际删除的文件。

## GF-03-R2 · MTP 复制部分成功时，结果遗漏已写入内容

**复现与影响**　通过批量粘贴复制一个包含两份 BIN 的 MTP 目录。第一份上传成功，第二份传输时断连。第一份 BIN 留在目标，任务只标记整个目录失败，未指出实际目标或已写入内容。已用模拟 MTP 复现。

**修复建议**　让批量结果和窗口能表示目录复制部分完成，返回实际目标目录、已确认写入的路径，以及中断原因。继续沿用副本自动改名和取消机制，报告实际输出路径。[MTP 复制与批量结果](../src/game_file_actions.py) · [粘贴结果展示](../src/templates/game-files.js)

- [ ] 模拟第一份 BIN 完成、第二份失败，后续顶层项未执行。结果和界面指向实际目标目录和已写入的 BIN，并显示部分完成。
- [ ] 用取消替代断连复验，区分取消与传输失败。完整成功的同名副本仍使用并显示最终自动分配的名称。

## GF-05-R1 · Finder 路径二次解码可能导入另一个文件

**复现与影响**　在 `100%20Complete/` 和 `100 Complete/` 各放置内容不同的 `Game.sfc`。将第一条路径交给原生拖放的 URL 与 DOM 桥接流程。系统 URL 经 Cocoa 解码后保持字面量 `%20`，pywebview 6.2.1 的桥接再次解码，将路径指向第二份文件。已用系统 NSURL 和锁定版本的桥接函数核对实际读取的字节。现有回调对未匹配路径还会按剩余列表顺序分配，多个来源的关联需一并验收。

**修复建议**　从本次原生拖放事件取得文件 URL，完整保留路径，只在 URL 转文件系统路径时解码。来源无法可靠关联时提示使用「添加游戏」。继续复用共用导入预览。[Finder 桥接](../src/desktop_window.py) · [文件页导入](../src/templates/game-files.js)

- [ ] 用上述双路径样本回归，确认传给导入预览的路径仍含字面量 `%20`，目标字节来自所拖入的文件。
- [ ] 在 macOS 应用包里从 Finder 验证文件、文件夹、中文、空格、百分号及不同目录下的同名来源。路径无法确认时显示提示，没有提交另一条路径。

## GF-05-R2 · 目录切换期间的拖入仍提交给旧目录

**复现与影响**　当前显示 A，发起进入 B 的目录请求并让响应延迟，在此期间触发拖入和 native 路径回调。A 仍保留在 `current`，落点校验通过，导入预览收到 A。已用实际前端事件处理函数复现。

**修复建议**　导航开始时清除旧拖放落点，目录加载期间暂停接收新落点。原生回调到达时核对该次事件绑定的页面、目录与导航版本。后续拖放不得使用前一次延迟到达的路径回调。[拖放、目录加载与导入预览](../src/templates/game-files.js)

- [ ] 延迟 B 的响应，在加载过程中拖入文件。A 和 B 均没有收到导入预览或写入请求，界面给出可重试反馈。
- [ ] 在 A 落下后延迟 native 回调，导航到 B 或关闭文件页。迟到回调未触发导入。B 加载完成后的新拖入使用正确目标，正常进入同一套冲突与复制流程。
